# Decisions log, D1–D93 (archived 22 Oct 2026)

> **Archived.** This is the decisions log as it stood on 21 Oct 2026, kept word for word.
> It was replaced on 22 Oct 2026 by the simplified set in [`../decisions.md`](../decisions.md),
> whose mapping table shows where each entry below now lives. Nothing here is in force.

The single record of **what** has been decided. One entry per decision, each with a short title. A change
is a new entry that supersedes an old one — entries are never edited to say
something different. Other documents refer to these IDs instead of restating
them. A fully replaced entry moves, unchanged apart from its pointer, to the
Superseded section at the end; it is never erased. An entry that is refined or
partly replaced stays in place and carries a pointer to the newer entry.

Status. D1–D24: agreed before the F1 decision pass. D25–D44: agreed at the close
of the F1 decision pass (30 Sep 2026). D45–D50: agreed in the F1 review
(1 Oct 2026). D51–D90: agreed in the F1 decision review (3 Oct 2026), which
checked every entry against the twelve v1 defects and against each other.
D91–D93: agreed in the rulings of 21 Oct 2026.

| D24 | **Model drafts.** The model's drafts are constrained, checked by code before a person sees them, and monitored for drift. Hallucination is limited and detected. It is never claimed to be zero. A new model version, prompt or playbook is used only after the full test set passes. **Refined by D53; clarified by D79.** |
| D25 | **Roles and views.** There is one decision owner, the PMO lead. The other actors are the team manager, Ops specialists and executives. There is one decision record per week. Code shows it as an ops view and an exec view, each with only the fields tagged for it. The prototype has one user who acts in every role, and each action is labelled with its role. **Terms defined in D88.** |
| D26 | **Colour rule.** Each metric is coloured against its target, according to its direction. "Higher is better" rates are amber up to 2% worse than target (relative to the target) and red beyond that. Low rates, counts and days use a band set per metric. Shown beside the colour: the week-over-week change; the change against the previous 4-week average (like-for-like while a dispute window is open); a 4-week sparkline; and "n/a" for the first 4 weeks. There are no graded states, no persistence rule and no seasonal targets. **Refined by D51 and D70.** |
| D28 | **Interventions and the record.** Every cause has at least one intervention, or a deferral with a reason. A cause and stage may have several interventions when each meets a different need, but never two of the same playbook type. Each intervention names its cause and stage and cites its evidence. Capacity is the overall limit. Nothing the model drafts is shown until the PMO lead has reviewed it. Every draft, edit and decision is kept in an append-only weekly record, with its status (pending review, reported, rejected, deferred), reviewer and time. A note is required on every reject or edit. **Rejects and edits as candidate cases: D91.** |
| D29 | **Playbook.** Interventions come from a playbook, a data file the PMO lead edits. Each entry has an owner role, an effort range, the causes it fits, whether it needs exec authority, and best-practice steps that are shown word for word. Code pre-filters the entries by suspected cause. There is no retrieval step. Off-playbook interventions are allowed. They are labelled and shown only after review. Playbook changes are approved by the PMO lead, versioned and re-tested. The model may only propose them. **Extended by D69 and D75.** |
| D30 | **Confidence and gaps.** Every suspected cause carries a confidence level (low, medium or high) and its evidence gaps. High confidence together with evidence gaps is a red line: the draft is rejected, retried once, then shown as "needs human review". Whether the model held back when it should have is a judgement metric. **Refined by D49; generalised by D68.** |
| D31 | **Simulated data.** The data is simulated: 1,500 partners, one invoice each per week, 52 weeks, English-only text, labelled as synthetic. The coloured metrics are payment accuracy, dispute rate, exception rate, dispute resolution within 5 days, processing cycle days and stuck invoices. Invoice volume is shown as context. Payment accuracy counts confirmed errors only. **"Confirmed" is defined in D88.** |
| D33 | **Git history.** The git history is not rewritten. |
| D34 | **Model against rules.** The model's clustering is compared with a rules-only baseline on the same dispute tickets. Both are scored against the confirmed cause and on lead time. The model is used for a part only where it beats the rules by an agreed margin and is never worse on red lines. Safeguards SG-01 to SG-06 apply. Decisions are routinely compared against the safeguard register. **Scoring clarified by D83; lead time defined in D88; rules baseline roles set by D92.** |
| D35 | **Issue lifecycle.** An issue moves through these stages: Detected, Contained, Cause confirmed, Corrected, Prevented, Closed. Exit criteria are checked in code. People move the stages. The model proposes actions and flags stalls. Metrics are tracked per invoice week. The dispute rate is the share of a week's invoices disputed within the two-week window. It is coloured on its current value and labelled "window open — provisional" until the week closes. The next update restates the final values and any colour change. The weekly ops and exec update shows the week number, performance, and each open issue's progress until it closes. **Partly replaced by D45 (who flags stalls); clarified by D73.** |
| D36 | **Framing and slices.** The product is framed around issues. The model spots patterns across dispute tickets and never names a root cause. People confirm causes after investigation. The build slices are: S1 metrics and capacity, S2 clustering, S3 contain, S4 lifecycle board and weekly update. |
| D37 | **Value measures.** Value is measured in two ways. Adoption: reported interventions actioned by their due week. Outcome: time to contain (the primary measure), the share of issues caught proactively, and the share of affected partners contacted before they disputed. Replaces D13. **Clarified by D52 and D62.** |
| D38 | **Prototype scope.** Built: metrics with colour and trends; capacity check; clustering against the rules baseline; Detect and Contain; review gate and audit record; weekly update; drift table in the scorecard. Illustrative, scripted by the generator and labelled "simulated outcome": Cause confirmed, Corrected, Prevented. Designed, not built: the real later-stage workflow, a playbook update workflow, a dashboard drift view, outcome tracking, retrieval over past issues. **Clarified by D62, D73 and D91.** |
| D39 | **Records and replay.** Records are plain-text, append-only weekly files. They are created locally and stored in git. The public app is a read-only replay that can show the state as of any week. **Replay scope clarified by D63.** |
| D40 | **No AI calls in public.** The public app makes no AI calls. The README explains how to reproduce the run locally. |
| D42 | **README status.** The README is short and has a generated status block, from F1 until the overview is written in W. |
| D44 | **Phasing.** F1 runs in one session, in slimmer form. Later documents and registers are added when they are first used. S4's size is set in its charter. **Partly replaced by D77 (F1 in one session).** |
| D45 | **Stalled issues.** Code detects stalled issues. It counts the days in the current stage from the recorded stage dates and compares them with a limit per stage, set in F2. An issue over its limit is marked overdue on the board and in the weekly update. The model only proposes the next action for an overdue issue, and that proposal is reviewed like any other draft. Replaces the part of D35 that had the model flag stalls. **Clarified by D73.** |
| D46 | **Overtime.** The team manager approves overtime, within the 48-hour limit. Extra FTEs remain an exec decision (D48). |
| D48 | **Capacity.** The baseline team is 5 FTE × 40 h. Each person has 4 h of protected time for meetings and admin, which leaves 180 productive hours a week, or 220 h with overtime. 48 h per person is a red line. Absence is not modelled; the team manager confirms availability. Workload = 60 h weekly payment run + 2 h per dispute (counted in the week it is opened) + 15 min per exception + 30 min per stuck invoice + the effort of reported issue interventions. Utilisation = workload ÷ productive hours, compared with a target ceiling set in F2. The check runs in every week that has open issues or amber or red metrics. Above the ceiling it proposes overtime first, then extra FTEs, which need exec authority. Both views show the improvement time remaining. Replaces D27. **Figures labelled as assumptions by D71.** |
| D49 | **Measured confidence.** Confidence is measured, not asserted. High: at least two independent evidence types agree and there are no gaps. Medium: one evidence type, or minor gaps. Low: thin or conflicting evidence. Code computes cluster size, field agreement and run-to-run consistency, and checks the model's label against them. Calibration is measured on the test set and shown in the drift table. The exact rules are set in F2. Refines D30. **Refined by D57.** |
| D50 | **Month-end and quarter-end.** Month-end and quarter-end weeks are marked in the data. Before proposing an issue, clustering compares a cycle week with the same point in earlier cycles. Only a pattern beyond the usual cycle is proposed. Colours stay on target (D26: no seasonal targets). The comparison rule is set in F2. **Clarified by D74.** |
| D51 | **Colour is the level.** Colour shows the level only. A metric beyond its red threshold is red, whether it is getting worse or recovering. It leaves red only when it is back inside the threshold. On the chart the trend line is neutral, and only amber and red weeks carry a coloured dot. Refines D26. |
| D52 | **Colour triggers nothing.** A metric's colour never opens an issue or creates an intervention by itself. The PMO lead may investigate, open an issue by hand (with or without dispute tickets) and add interventions to it. These are recorded like any other. An issue opened by hand before partners dispute counts as caught proactively (D37). |
| D53 | **No numbers from the model.** The model writes no numbers of its own. Every number in a draft must already be in the evidence that code gave the model, or in the playbook entry. Code checks this before the draft is shown. Ticket references and week numbers quoted from the evidence are allowed. Refines D24. |
| D54 | **No impact forecast.** No expected impact is shown for an intervention. It states what it addresses and its effort. Value is measured afterwards (D37). |
| D55 | **Ticket text.** Ticket text is written as if by someone who does not know the cause. It never restates a weekly metric value. It may contain the writer's own guess at the cause, and a share of those guesses are wrong (the share is set in F2). Code scans every generated ticket before the data is accepted. |
| D56 | **Claims in tickets.** A cause stated in ticket text is a claim by its writer, not a finding. Claims are recorded as "claimed in tickets", with the count computed by code. They are shown to the PMO lead and Ops on the review screen as a starting point. They never count as evidence for confidence (D49). They never appear in the ops or exec view, or as the basis of an intervention, unless the PMO lead confirms them. The model adds nothing the tickets do not say. |
| D57 | **Derived figures.** A figure computed from other metrics is never evidence. Workload and utilisation are capacity views only. Evidence types are a fixed list set in F2. Metrics that move together by construction count as one type. Refines D49. |
| D58 | **Escaping.** All text that comes from the model or from data is shown as plain text and escaped before rendering. This covers model output, ticket text, playbook steps and notes, in the local run and in the replay. Unescaped text reaching the page is a red line. |
| D59 | **One home for rules.** `decisions.md` is the only place where a rule or a number is stated. Other tracked documents cite the ID. Where a rule's wording must appear, a script copies it in. |
| D60 | **Planned or built.** Whether something is planned or built is generated from the registers into every document that mentions it, starting in F1. Nothing is described as existing unless it is marked built. Review stamps start in F3 and the claims check in S1. Replaces D43. |
| D61 | **Terms.** Each concept has one preferred term. The registers list it with the terms it replaces, and code checks it. It applies to all active entries and to all other documents. Superseded entries stay as written. The first terms are: "the model" for the AI inside the product, replacing "the AI" and "the agent"; "the builder" for the agent that builds the code; "suspected cause" for a cause before it is confirmed, replacing "proposed cause". |
| D62 | **Measures are simulated.** The measures in D37 are computed from the weekly record of the simulated run and labelled "simulated". A containment intervention that involves contacting partners records which partners were contacted and when. Tracking whether an intervention actually worked is not built. Clarifies D37 and adds the contact record to D38's built scope. |
| D63 | **The year.** Weeks 1–26 are history. Code generates them and the model does not run. Weeks 27–39 are the scenario quarter. Each kind of scenario plays out over several weeks and shows the model's path. The scenario quarter contains at least one unrecognised pattern. Weeks 40–52 are the held-out quarter. It has the same kinds of scenario in new instances, plus a few kinds not used in the scenario quarter. For those, the expected answer is "requires human review" (D64). The builder never reads the held-out quarter, and it is run once after S4. The replay shows the full year of metrics, the model's path in the scenario quarter, and the held-out quarter once it has been run. The number of scenarios is set in F2. |
| D64 | **Unrecognised patterns.** When a pattern in the tickets matches no cause on the cause list, the model proposes no cause. The intervention shown is the fixed text "requires human review", with the tickets and the counts computed by code. "No issue this week" is equally a valid answer. |
| D65 | **Two labellers.** Two fresh agents with no project context label each case independently. The author decides disagreements before seeing which label came from whom. The author also spot-checks a sample of the labels both agreed on (sample size set in F2). Held-out disagreements are handled as in D76. |
| D66 | **Sealing the held-out quarter.** The held-out quarter's scenario definitions and the agents' labels are kept in a folder outside the project. Build sessions are never connected to that folder. A fingerprint of the files is committed when they are written in F3. The files enter the project only for the final run after S4, when the fingerprint is checked. Enforces D63. |
| D67 | **Quarter boundary.** A ticket belongs to the quarter of the week it is opened. Every scenario in the scenario quarter starts early enough to reach Contained by week 39. Every held-out scenario starts in week 40 or later, depends on no earlier issue, and reaches Contained by week 52. Scripted later stages may continue past week 39. The dispute rate for weeks 38 and 39 stays "window open — provisional" during the build and is finalised in the final run. Clarifies D63. |
| D68 | **Failed checks.** A draft that fails any code check is rejected and not shown. The model is asked once more. If the second draft also fails, the item is shown with the fixed text "requires human review" and the name of the failed check. Code never repairs a draft to make it pass. Every rejected draft is kept in the weekly record. Generalises D30 and replaces its wording "needs human review". |
| D69 | **Cause list.** The cause list is a data file the PMO lead edits, kept with the playbook. Each cause has a name, a short description, and the ticket fields or metrics that would support it. The model may choose a suspected cause only from this list. Anything else falls under D64. Changes are approved by the PMO lead, versioned and re-tested, as for the playbook (D29). The first version is set in F2. |
| D70 | **Metrics register.** Each metric's definition, direction and target are held in the metrics register. This is a data file owned by the PMO lead and set in F2. It also holds the amber band for every metric except "higher is better" rates, whose band is set by D26. A week is green when it meets the target, amber inside the band, and red beyond it. Changes are approved, versioned and re-tested, as for the playbook (D29). |
| D71 | **Assumptions.** The effort figures in D48 and the targets and bands in the metrics register are assumptions. They are based on the author's operating experience, not on measurements. They are labelled as assumptions wherever they are shown. Applies D12. |
| D72 | **Issues opened by hand.** For an issue opened by hand, the PMO lead chooses the suspected cause from the cause list or marks it "under investigation". Code shows the playbook entries for that cause. The PMO lead selects from them or writes their own, and enters the effort and due week for any they write. The model drafts nothing for this issue. The cause is labelled "entered by PMO lead" and carries no confidence level. The capacity check applies as for any intervention (D48). When later tickets form a pattern, the PMO lead may attach them to an existing issue in review instead of opening a new one. The model does not merge issues by itself. |
| D73 | **Where the model stops.** The model drafts only for issues that are not yet Contained. It proposes the possible issue with its suspected cause, and the interventions to contain it. From Contained onward, every stage (including Closed) is scripted by the generator and labelled "simulated outcome". The model drafts nothing there. The PMO lead moves an issue to Contained once the exit criteria checked by code are met. Code always marks an overdue issue (D45). The model proposes a next action only if the issue is not yet Contained. Clarifies D35, D38 and D45. |
| D74 | **Year-end.** The simulated year has no separate year-end effect. Week 52 behaves as an ordinary quarter-end. Where a cycle week has fewer earlier cycles than the minimum set in F2, it is labelled "no cycle comparison available". Any pattern in it is left to the PMO lead to judge. Clarifies D50. |
| D75 | **Due week.** Code sets an intervention's due week: the week it is reported plus the time allowed in its playbook entry. The PMO lead may change it in review. The model sets no dates. Adds "time allowed" to the fields of a playbook entry (D29). |
| D76 | **Labelling the held-out quarter.** In F3, two fresh agents label both quarters independently (D65). Code compares their labels with the expected answers. A held-out scenario is kept if at least one agent's label matches its expected answer, and the disagreement is logged for the author after the freeze. If neither label matches, the scenario is rewritten before the fingerprint is taken. The author and the builder see only the counts. The author does not read the held-out quarter until the S4 build is frozen. The author then labels it before the final run, without seeing any model output for it. Those labels are fingerprinted before the run. |
| D77 | **Phases and gates.** The build runs in eight phases: F1 frame and decisions, F2 requirements and dataset design, F3 harness, S1 to S4 the build slices (D36), and W wrap-up. The author and Claude work F1 to F3 and W together. The builder, an agent working under a charter (D21), builds S1 to S4. A phase may take several sittings. Each phase ends with a gate. At the gate, a fresh agent with no project history reviews all tracked files. Findings rated HIGH block the gate. The rest are fixed in one batch. Replaces "F1 runs in one session" in D44. |
| D78 | **Labelling guide.** Labellers work from a labelling guide that the author writes or approves. It says what each cause looks like in the data, and when the answer is "no issue" or "requires human review". Supports D65. |
| D79 | **Full test set.** "The full test set" in D24 means the scenario quarter. Once the held-out quarter has been run, any later change to the model version, instructions, cause list or playbook is stated publicly as made after the holdout was used. Clarifies D24. |
| D80 | **Rules and data files.** `decisions.md` holds the rules. Data files hold the contents those rules govern: the playbook, the cause list, the metrics register and the safeguard register. Documents cite both and restate neither. Clarifies D59. |
| D81 | **What each phase adds.** Each of F1 to F3 and W adds its section of the operating model. Each slice adds its charter and scorecard. A section explains the method and cites IDs. The full narrative is written in W. Clarifies D11. |
| D82 | **No outside validation.** No outside person validates the prototype. The author, who also plays the PMO lead, judges fitness for purpose. This is stated as a limitation wherever validation is mentioned. Independent validation is designed, not done. Replaces the outside-validation part of D23. |
| D83 | **Answer sheet.** The model is scored against the expected answer written into each scenario's definition. Labels check the quality of the scenarios; they are not the answer sheet. If labels show a scenario to be faulty, it is fixed in the scenario quarter. In the held-out quarter it is excluded from the score and reported as excluded, with the reason. |
| D84 | **Red lines.** The red lines are: high confidence despite evidence gaps (D30); the 48-hour limit (D48); a number not in the evidence (D53); a ticket claim used as cause or evidence (D56); a cause not on the cause list (D64); unescaped text on the page (D58). Zero tolerance means no violating draft is ever shown. How often drafts are rejected is tracked as a drift measure. Clarifies D8. |
| D85 | **Builder limits.** The builder edits only the paths its charter names. It stops and escalates in these cases: at the iteration or spend cap; when the same failure occurs twice; when a fix would need a test, label or requirement changed. It prepares commits and never pushes. Extends D21. |
| D86 | **Charter contents.** A charter states: the goal, as a target scorecard state; the paths the builder may edit; the iteration and spend caps; when the slice is done; and where the author must approve. |
| D87 | **Privacy.** No internal tools or people are named. Extends D14. |
| D88 | **Definitions.** *The author* is the project's owner; *PMO lead* is a role in the simulated operation, which the author plays in the prototype (D25). A *possible issue* is a cluster proposed by code or the model; it becomes an *issue* when the PMO lead accepts it in review. The *review screen* is where drafts and ticket claims are shown before anything reaches the ops or exec view. An *overtime proposal* is a capacity proposal, not an intervention. *Lead time* is how many weeks sooner a method proposes a possible issue, counted from the week the planted pattern begins. A payment error is *confirmed* when a back-payment or a correction to a payment is made, whether a dispute prompted it or Ops found it first. |
| D89 | **Holdout.** The holdout is the held-out quarter, weeks 40–52 (D63). A separate agent writes it. It is sealed (D66), bounded (D67), labelled and run once after S4 (D76), and scored against expected answers (D83). No outside person uses it (D82). Replaces D41. |
| D90 | **Labelling.** The scenario quarter's test cases are written by Claude; the held-out quarter's by a separate agent. Labelling follows D65, D76 and D78. Safeguards SG-07 to SG-11 apply. Replaces D47. |
| D91 | **Overrides as candidate cases.** Every reject or edit by the PMO lead, with its note (D28), is a candidate test case. The author decides whether it enters the test set. An accepted candidate is added as a new case; it never changes an existing label (SG-09). The record that captures rejects and edits is built (D28); turning them into test cases is designed, not built. Clarifies D38. |
| D92 | **Rules baseline roles.** The PMO lead writes the rules baseline (D34): the rules the team would use without the model. The author freezes it before any scoring. Clarifies D34 and SG-01. |
| D93 | **Weekly order.** Each week runs in this order: DEC-1; DEC-4 on the hours already committed; DEC-2; DEC-3, drafting within the hours left; DEC-4 again on the drafts; then the PMO lead's review. Sets the order of the sub-decisions in D36. |
